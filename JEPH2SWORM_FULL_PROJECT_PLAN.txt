1. VISION & OVERVIEW
================================================================================

JEPH2SWORM is an autonomous AI development swarm that transforms a single
product idea into a fully built, tested, and deployed software application.

The user provides an idea. The swarm does everything else.

No prompting fatigue. No context loss. No half-built projects. No wasted tokens.

The system consists of TWO products that work together:

  A) VS CODE EXTENSION ("jeph2sworm")
     - AI chat sidebar (like Copilot)
     - Multi-agent swarm that writes, builds, tests, deploys code
     - Autonomous file system access
     - Terminal & package manager control
     - Real-time agent collaboration visible to user

  B) CHROME EXTENSION ("jeph2sworm-browser")
     - AI-controlled browser powered by browser-use library
     - Screenshots, screen recording, DevTools access
     - GUI interaction for design tools (Figma, Canva, etc.)
     - Live website testing (not just curl)
     - Asset downloading, form filling, research

Together, these two extensions create a complete autonomous development
environment where AI agents work like a real dev team.

CORE PRINCIPLES:
  - Zero-permission friction (user grants access once, agents work freely)
  - Zero context loss (Brain maintains everything)
  - Zero hallucination tolerance (strict rules engine)
  - Real-time parallelism (all roles work simultaneously)
  - Production-grade output (120+ test cycles before "done")
  - Secure by default (ai.env with bitcoin-address-grade passwords)

    D) WEBVIEW PANELS

       - Test results dashboard
       - Deployment status
       - ai.env viewer (secure, masked by default)

    - "Jeph2Sworm: Connect API Key"
    - "Jeph2Sworm: View Agent Activity"
    - "Jeph2Sworm: View Brain Memory"

6. MULTI-AGENT SWARM SYSTEM
================================================================================

6.1 CONCEPT
    The swarm is a team of specialized AI agents, each with a defined role,
    working in parallel on the same project. They communicate through a
    shared Brain (memory system) and a real-time event bus.

    Unlike sequential AI workflows (ask -> respond -> ask -> respond),
    ALL agents work SIMULTANEOUSLY. The backend developer doesn't wait for
    the frontend developer. The tester doesn't wait for deployment. They
    all work at the same time and coordinate through the Brain.

6.2 AGENT LIFECYCLE
    1. SPAWN: Orchestrator creates agent with role, context, and tools
    2. PLAN: Agent reads Brain, understands current state, plans tasks
    3. EXECUTE: Agent works on tasks (writes code, runs commands, etc.)
    4. REPORT: Agent updates Brain with results, artifacts, status
    5. COORDINATE: Agent reads updates from other agents, adjusts plan
    6. LOOP: Steps 3-5 repeat until agent's tasks are complete
    7. IDLE: Agent enters monitoring mode, reactivates if needed

6.3 PARALLELISM MODEL
    - Each agent runs as an independent async task
    - Agents have their own LLM context window
    - Agents share state through Brain (not by passing messages directly)
    - Event bus notifies agents of relevant updates
    - No agent blocks another agent
    - Orchestrator resolves conflicts (e.g., two agents editing same file)

6.4 CONFLICT RESOLUTION
    - File-level locking: Only one agent can write to a file at a time
    - Merge strategy: If conflict, Brain decides which change wins
    - Priority chain: PM > Brain > Tester > Backend > Frontend > UX > DevOps
    - All conflicts logged for user review

6.5 AGENT COUNT & SCALING
    Default: 6 agents (PM, Backend, Frontend, UX, Tester, DevOps)
    Expandable: Up to 12 agents for complex projects
    Possible additional roles:
    - Database Architect
    - Security Auditor
    - Documentation Writer
    - API Designer
    - Mobile Developer
    - Performance Engineer

7. BRAIN & SHARED MEMORY
================================================================================

7.1 WHAT IS THE BRAIN?
    The Brain is the central memory and decision-making system. It's NOT
    an agent itself — it's a shared data structure that all agents read
    from and write to. Think of it as the project's "single source of truth."

7.3 PERSISTENCE
    - Brain is stored in .jeph2sworm/ directory in the project root
    - Gitignored by default (contains sensitive data references)
    - Can be exported/imported for project continuity
    - Backed up at every milestone

7.4 CONTEXT MANAGEMENT
    - Each agent gets a SUMMARY of the full Brain (not the entire thing)
    - Brain uses RAG (Retrieval-Augmented Generation) for relevant context
    - Context window is optimized per-agent (backend agent gets API contracts,
      frontend agent gets UI specs, etc.)
    - Stale context is archived, not deleted

8. AGENT ROLES & RESPONSIBILITIES

ROLE 1: PROJECT MANAGER (PM)
---------------------------------------------------------------------
  Purpose:   Overall project coordination, user communication, planning
  Tasks:
    - Gather project requirements from user
    - Break project into milestones and tasks
    - Assign tasks to agents
    - Monitor progress and resolve blockers
    - Communicate status updates to user
    - Make final decisions on scope and priorities
  Tools:
    - Brain read/write
    - User chat interface
    - Task board management
  LLM Usage: Moderate (planning, summarization)


ROLE 2: BRAIN / ARCHITECT
---------------------------------------------------------------------
  Purpose:   Technical architecture, decision-making, context management
  Tasks:
    - Design system architecture
    - Choose tech stack (or use user-specified)
    - Define API contracts
    - Define database schema
    - Maintain architecture documentation
    - Resolve technical conflicts between agents
    - Feed relevant context to each agent
  Tools:
    - Brain read/write (primary maintainer)
    - Architecture diagram generation
    - Code analysis
  LLM Usage: High (complex reasoning, architecture decisions)


ROLE 3: BACKEND DEVELOPER
---------------------------------------------------------------------
  Purpose:   Server-side code, APIs, database, business logic
  Tasks:
    - Set up backend project structure
    - Implement API endpoints
    - Set up database (schema, migrations, seeds)
    - Implement authentication/authorization
    - Implement business logic
    - Write backend unit tests
    - Create API documentation
    - Update API contracts in Brain as endpoints are built
  Tools:
    - File system (read/write code)
    - Terminal (run server, install packages, run migrations)
    - Brain (read API contracts, write endpoint status)
  LLM Usage: Very High (code generation, debugging)
  Sends To:
    - Frontend: API endpoint URLs, request/response shapes
    - DevOps: Server requirements, environment variables needed
    - Tester: API endpoints ready for testing


ROLE 4: FRONTEND DEVELOPER
---------------------------------------------------------------------
  Purpose:   Client-side code, UI implementation, state management
  Tasks:
    - Set up frontend project structure
    - Implement UI components based on UX designs
    - Connect to backend APIs
    - Implement state management
    - Implement routing
    - Handle responsive design
    - Write frontend tests
    - Implement real-time features (WebSocket, SSE)
  Tools:
    - File system (read/write code)
    - Terminal (run dev server, install packages)
    - Brain (read UI specs, API contracts)
    - Browser extension (visual testing)
  LLM Usage: Very High (code generation, CSS, component logic)
  Receives From:
    - Backend: API endpoints and schemas
    - UX: Component designs, layout specs, color palette


ROLE 5: UI/UX DESIGNER
---------------------------------------------------------------------
  Purpose:   User interface design, user experience, visual identity

  Tools:
    - Browser extension (access Figma, Canva, design tools)
    - Brain (write design specs, read project requirements)
    - Screenshot tool (capture design references)
  LLM Usage: Moderate (design decisions, CSS generation)
  Sends To:
    - Frontend: Component specs, CSS values, asset URLs
    - PM: Design mockup links/screenshots for user approval


ROLE 6: TESTER / QA ENGINEER
---------------------------------------------------------------------
  Purpose:   Quality assurance, testing, bug reporting
  Tasks:
    - Write unit tests for all code
    - Write integration tests
    - Write end-to-end tests
    - Run tests (120+ cycles)
    - Report bugs with reproduction steps
    - Verify bug fixes
    - Test on deployed environment (via browser extension)
    - Generate test evidence (screenshots, recordings)
    - Performance testing
    - Security testing (basic)
    - Accessibility testing
  Tools:
    - File system (write test files)
    - Terminal (run test suites)
    - Browser extension (E2E testing, visual testing)
    - Brain (read test plans, write results)
  LLM Usage: High (test generation, bug analysis)
  Testing Protocol:
    - Run 1-30: Unit tests (each module individually)

    - Database hosting/backups

  Tools:
    - File system (Dockerfile, docker-compose, CI configs)
    - Terminal (docker commands, deploy scripts)
    - Browser extension (deploy via web dashboards)
    - Brain (read server requirements, write deploy status)
  LLM Usage: Moderate (infrastructure decisions, config files)
  Receives From:
    - Backend: Server requirements, env vars needed

9. REAL-TIME COMMUNICATION PROTOCOL
================================================================================

9.1 EVENT BUS
    All agents communicate through a central event bus. Events are typed
    and structured. Every event is logged in the Brain.

9.2 EVENT TYPES

    AGENT_STATUS_CHANGED
      { agent_id, role, new_status, current_task }

    TASK_COMPLETED
      { agent_id, task_id, result, artifacts[] }

    TASK_BLOCKED
      { agent_id, task_id, reason, needs_from_agent }

    FILE_CREATED
      { agent_id, file_path, purpose }

    FILE_MODIFIED
      { agent_id, file_path, changes_summary }

    API_ENDPOINT_READY
      { agent_id, method, path, request_schema, response_schema }

    DESIGN_READY
      { agent_id, component_name, design_url, css_specs }

    TEST_RUN_COMPLETE
      { agent_id, run_number, passed, failed, evidence[] }

    BUG_REPORTED
      { agent_id, title, description, steps_to_reproduce, severity }

    BUG_FIXED
      { agent_id, bug_id, fix_description, files_changed[] }

    DEPLOY_STATUS
      { agent_id, environment, status, url }

    ERROR_OCCURRED
      { agent_id, error_type, message, stack_trace }

    USER_MESSAGE
      { content, requires_response }

    BRAIN_UPDATED
      { section, changes_summary }

    CREDENTIAL_CREATED
      { key_name, purpose, created_by }

9.3 MESSAGE FORMAT (WebSocket)

    {
      "event": "TASK_COMPLETED",
      "source": "backend-dev",
      "timestamp": "2026-02-08T10:30:00Z",
      "data": {
        "task_id": "task-042",
        "result": "User authentication API implemented",
        "artifacts": [
          "src/api/auth/login.ts",
          "src/api/auth/register.ts",
          "src/middleware/auth.ts"
        ]
      }
    }

9.4 UI RENDERING
    All events are rendered in the VS Code sidebar as a real-time feed.
    Users see messages like:

    [10:30] Backend Dev: ✅ Auth API complete — POST /api/auth/login ready
    [10:30] Frontend Dev: 🔄 Connecting login form to /api/auth/login
    [10:31] Tester: 📝 Writing auth tests...
    [10:31] DevOps: 🐳 Added JWT_SECRET to environment config
    [10:32] UX Designer: 🎨 Login page design ready — sending to Frontend

10. LLM PROVIDER INTEGRATION
================================================================================

10.1 SUPPORTED PROVIDERS (Minimum 5, Target 8+)

    1. OpenAI (GPT-4o, GPT-4.1, o3)
    2. Anthropic (Claude Opus 4, Claude Sonnet 4)
    3. xAI (Grok-3)
    4. Google (Gemini 2.0 Pro, Gemini 2.5)
    5. DeepSeek (DeepSeek-V3, DeepSeek-R1)
    6. Mistral (Mistral Large, Codestral)
    7. Meta (Llama 4 via Together/Groq)
    8. Cohere (Command R+)

10.2 LLM ROUTER
    The LLM Router decides which provider/model to use for each agent
    and each task. Strategy:

    - Coding tasks: Use best code model (GPT-4.1, Claude Opus, DeepSeek)
    - Planning tasks: Use best reasoning model (o3, Claude Opus)
    - Design tasks: Use multimodal model (GPT-4o, Gemini)
    - Quick tasks: Use fastest model to save tokens
    - Fallback: If primary provider fails, auto-switch to backup

10.3 API KEY MANAGEMENT
    - User provides API key(s) during setup
    - Keys stored in VS Code SecretStorage (encrypted)
    - Can use multiple providers simultaneously
    - Token usage tracked per agent, per session
    - Budget limits configurable

10.4 TOKEN OPTIMIZATION
    - Context compression before LLM calls
    - Caching for repeated queries
    - Incremental updates (don't re-send entire context)
    - Smart truncation (keep most relevant context)
    - Cost estimation before expensive operations

11. SECURITY & RULES ENGINE
================================================================================

11.1 CORE RULES (HARD-CODED, CANNOT BE OVERRIDDEN)

    RULE 1: NEVER DELETE USER DATA
      - Agents can create and modify files
      - Agents CANNOT delete files outside the project directory
      - No rm -rf, no format, no destructive operations on system files

    RULE 2: NEVER CORRUPT PROJECT
      - Every file write is preceded by a backup
      - Git commit at every milestone
      - Rollback capability for every change

    RULE 3: NO HALLUCINATION IN CRITICAL PATHS
      - All API endpoints must be verified (actually callable)
      - All imports must resolve (no fake packages)
      - All environment variables must have values
      - All URLs must be valid
      - Tester validates all claims

    RULE 4: STAY IN SCOPE
      - Agents only work on the described project
      - No accessing files outside workspace
      - No network requests to unauthorized domains
      - No installing system-level packages without user's sudo password

    RULE 5: TRANSPARENT OPERATIONS
      - Every terminal command logged
      - Every file change logged
      - Every LLM call logged
      - Every decision documented in Brain
      - User can audit everything at any time

    RULE 6: CREDENTIAL SECURITY
      - Generated passwords must be 32+ characters
      - Must include: uppercase, lowercase, numbers, symbols
      - Strength equivalent to bitcoin address entropy
      - All secrets stored ONLY in ai.env
      - Never hardcoded in source files
      - ai.env added to .gitignore automatically

    RULE 7: NO EXTERNAL DATA EXFILTRATION
      - Agents never send project code to external services
        (except the LLM provider for inference)
      - No telemetry without consent
      - No third-party API calls without user knowledge

    RULE 8: GRACEFUL FAILURE
      - If an agent errors, it reports to Brain and retries
      - If retry fails 3x, escalate to PM
      - Never leave half-written files
      - Never crash silently

11.2 RULES ENGINE IMPLEMENTATION
    - Rules are checked BEFORE every action (pre-execution hook)
    - Rules are checked AFTER every action (post-execution validation)
    - Rules violations are logged and blocked
    - User is notified of any rule violations

13. BROWSER-USE INTEGRATION
================================================================================

13.1 HOW IT WORKS
    browser-use is a Python library that enables AI agents to control
    web browsers. We integrate it as the backend engine for the Chrome
    extension.

    Flow:
    1. Agent (e.g., Tester) needs to test deployed website
    2. Agent sends command to Browser Controller
    3. Browser Controller uses browser-use to:
       a. Launch/connect to Chrome instance
       b. Navigate to URL
       c. Interact with page (click, type, scroll)
       d. Capture screenshot/recording
       e. Read DevTools data
    4. Results sent back to agent via event bus
    5. Agent processes results and updates Brain

13.2 BROWSER-USE CAPABILITIES WE USE

    - Agent class: Main agent for browser automation
    - Browser class: Browser instance management
    - Multi-provider LLM support (aligns with our LLM Router)
    - Custom tools/actions
    - Screenshot capture
    - DOM element extraction
    - Click, type, scroll actions
    - Navigation
    - Tab management

13.3 CUSTOM BROWSER ACTIONS WE BUILD ON TOP

    - screen_record(duration): Record browser screen for N seconds
    - devtools_console_logs(): Get all console output
    - devtools_network(): Get network requests/responses
    - devtools_performance(): Get performance metrics
    - download_asset(url, path): Download file to project
    - gui_design_tool(tool, action): Interact with design tools
    - fill_deployment_form(provider, config): Auto-deploy via web UI
    - visual_regression(baseline, current): Compare screenshots
    - accessibility_audit(url): Run accessibility checks

13.4 CHROME EXTENSION <-> BROWSER-USE BRIDGE
    - Chrome extension connects to Python backend via WebSocket
    - Python backend runs browser-use agent
    - Chrome extension provides additional capabilities:
      * Native screenshot (higher quality)
      * MediaRecorder API (screen recording)
      * DevTools panels (deeper inspection)
      * Extension popup (user controls)
    - Two-way sync: browser-use actions reflected in Chrome extension UI

15. TESTING PHILOSOPHY (120x TEST CYCLES)
================================================================================

15.1 WHY 120 CYCLES?
    Most AI-generated code is tested 0-1 times. We test 120+ times because:
    - First 30 runs catch obvious bugs
    - Runs 31-60 catch integration issues
    - Runs 61-90 catch edge cases
    - Runs 91-110 catch rare conditions
    - Runs 111-120 confirm everything works together
    - More runs = more confidence = production-ready code

15.2 TEST TYPES

    UNIT TESTS (Runs 1-30)
    - Every function tested individually
    - Every edge case covered
    - Mock external dependencies
    - Aim: 95%+ code coverage

    INTEGRATION TESTS (Runs 31-60)
    - API endpoints tested with real database
    - Frontend-backend integration
    - Third-party service integration
    - Database operations (CRUD, transactions)

    END-TO-END TESTS (Runs 61-90)
    - Full user flows in browser (via browser-use)
    - Login -> Navigate -> Action -> Verify
    - Multi-user scenarios
    - Cross-browser/device testing

    EDGE CASE TESTS (Runs 91-110)
    - Invalid inputs
    - Network failures
    - Concurrent users
    - Large data sets
    - Empty states
    - Permission violations

    REGRESSION TESTS (Runs 111-120)
    - All previous tests re-run
    - Visual regression (screenshot comparison)
    - Performance regression
    - Security regression

15.3 EVIDENCE COLLECTION
    Every test run produces:
    - Test runner output (pass/fail per test)
    - Screenshots (if browser-based)
    - Console logs
    - Network request logs
    - Code coverage report
    - Performance metrics
    - Timestamp and run number
    All stored in .jeph2sworm/test_evidence/

15.4 DONE CRITERIA
    Project is "DONE" when:
    [x] All 120 test runs pass with zero failures
    [x] Code coverage >= 90%
    [x] No critical/high security vulnerabilities
    [x] Performance within acceptable bounds
    [x] Visual regression 0% different from design
    [x] All API endpoints return correct responses
    [x] All user flows complete successfully
    [x] Deployment successful and verified
    [x] ai.env complete with all credentials
    [x] Documentation generated

25. RISKS & MITIGATIONS
================================================================================

RISK 1: Token Cost Explosion
  Impact: High
  Mitigation:
    - Context compression
    - Smart caching
    - Model selection (use cheaper models for simple tasks)
    - Token budget per project with warnings
    - User-controlled spending limits

RISK 2: Hallucination in Code
  Impact: Critical
  Mitigation:
    - 120 test cycles catch hallucinated imports/APIs
    - Rules engine validates all file operations
    - Tester agent verifies every claim
    - Brain cross-references all agent outputs
    - Static analysis before committing code

RISK 3: Security of Machine Password
  Impact: Critical
  Mitigation:
    - Stored in VS Code SecretStorage (OS keychain)
    - Never written to disk or logs
    - Only used for explicit sudo operations
    - User can revoke at any time
    - Operations requiring password are logged

RISK 4: Agent Conflicts
  Impact: Medium
  Mitigation:
    - File-level locking
    - Priority chain
    - Conflict resolution by Brain
    - All conflicts logged
    - Rollback capability

RISK 5: Browser Extension Security
  Impact: High
  Mitigation:
    - Minimal permissions (only active tab when needed)
    - No data collection
    - Local-only communication (localhost WebSocket)
    - Open source for audit
    - CSP (Content Security Policy) headers

RISK 6: Rate Limiting by LLM Providers
  Impact: Medium
  Mitigation:
    - Request queuing with backoff
    - Multi-provider fallback
    - Caching to reduce calls
    - Batch requests where possible
